# Database Specification

This is the Version 1.0 logical baseline. Do not silently alter it.

## users
- user_id (PK)
- full_name
- email (unique)
- role: Student | Coordinator | Supervisor | ProgramHead | Admin
- account_status: pending | active | rejected | inactive
- created_at
- updated_at

Passwords are managed by the approved authentication provider, not stored as plaintext application fields.

## students
- student_id (PK)
- user_id (FK, unique)
- student_number (unique)
- course
- year_level
- required_hours
- status

## coordinators
- coordinator_id (PK)
- user_id (FK, unique)
- department

## supervisors
- supervisor_id (PK)
- user_id (FK, unique)
- company_id (FK)
- position

## program_heads
- program_head_id (PK)
- user_id (FK, unique)
- department_or_program

## admins
- admin_id (PK)
- user_id (FK, unique)

## companies
- company_id (PK)
- company_name
- address
- contact_person
- contact_email
- contact_number
- status
- created_at
- updated_at

## student_assignments
- assignment_id (PK)
- student_id (FK)
- company_id (FK)
- supervisor_id (FK)
- start_date
- end_date (nullable)
- assignment_status
- created_at

## attendance
- attendance_id (PK)
- student_id (FK)
- assignment_id (FK)
- attendance_date
- time_in
- time_out (nullable)
- time_in_selfie_path
- time_out_selfie_path
- qr_validation_status
- verification_status
- late_status
- sync_status
- created_at
- updated_at

## reports
- report_id (PK)
- student_id (FK)
- report_type
- file_path
- submission_date
- status
- remarks
- created_at
- updated_at

## evaluations
- evaluation_id (PK)
- student_id (FK)
- supervisor_id (FK)
- performance_score (only if approved evaluation form uses it)
- feedback
- evaluation_date
- created_at

## notifications
- notification_id (PK)
- sender_user_id (FK, nullable for system events)
- receiver_user_id (FK)
- message
- notification_date
- status

## internship_progress
- progress_id (PK)
- student_id (FK, unique)
- completed_hours
- remaining_hours
- progress_status
- updated_at

## Relationships
- One user has one role profile.
- One company may have many supervisors and student assignments.
- One supervisor may supervise many assigned students.
- One student may have assignment history.
- One student has many attendance records and reports.
- One student may have multiple evaluations if institutional policy permits.
- One student has one current progress record.
- One user may receive many notifications.

## Unresolved Data Details
Exact evaluation fields, report types, schedule model, retention-policy data, and official program reference data must be confirmed before their dependent features are finalized.
