# Security Specification

## Principles
- deny by default;
- enforce authorization on backend;
- use approved authentication provider;
- never store plaintext passwords;
- never expose privileged backend secrets in clients;
- never trust client-supplied role values;
- validate untrusted input;
- protect sensitive files.

## Authentication
Students self-register into pending status. Coordinator approves legitimate student registrations. Password recovery uses secure email-based reset. One user has one role.

## Authorization
Role checks must also consider ownership/assignment:
- Student: own records.
- Supervisor: assigned students for supervisor-authorized functions.
- Coordinator: approved OJT management scope.
- Program Head: approved monitoring scope.
- Admin: technical administration, not automatic academic authority.

## Attendance Security
- backend validation where required;
- selfies are manual evidence, not facial recognition;
- offline records remain pending until server validation;
- client time alone does not guarantee credited hours;
- duplicates/conflicts must be handled safely.

## Files and Images
Use private storage for sensitive selfies and protected OJT files. Do not expose permanent public URLs for sensitive content without explicit approval.

## Secrets
Use environment variables/secret management. Never commit secrets. Never place privileged service keys in mobile/browser clients.

## Privacy and Retention
Selfie and record retention periods require approved institutional policy. Do not invent legal retention periods.

Rate Limiting and Abuse Prevention
Purpose
Rate limiting protects the system from:
* brute-force login attempts;
* credential stuffing attacks;
* automated spam submissions;
* excessive API requests;
* denial-of-service attempts;
* accidental client-side request loops.
Rate limiting is a security and reliability requirement and must be applied to public-facing and sensitive operations.

General Rules
* Rate limiting must be enforced on the backend.
* Client-side controls (disabled buttons, timers, or hidden UI elements) are not sufficient.
* Rate limits must be applied consistently across web and mobile clients.
* Exceeding a rate limit must never bypass authentication or authorization rules.

Protected Operations
The following operations require rate limiting:
Authentication
* sign in;
* student registration;
* password reset requests;
* account approval actions.
Attendance
* Time In requests;
* Time Out requests;
* QR validation requests;
* attendance synchronization requests.
File Operations
* report or requirement uploads;
* selfie uploads;
* file download requests where appropriate.
Notifications
* announcement creation;
* notification dispatch operations.
Administrative Actions
* account activation or deactivation;
* role or permission changes;
* high-impact configuration changes.

Rate Limiting Strategy
The implementation should support multiple rate-limiting layers where appropriate:
* per IP address;
* per authenticated user;
* per account;
* per device or client identifier where technically feasible.
Different operations may have different limits based on risk and expected usage.
Examples:
* authentication requests should be more strictly limited than ordinary data retrieval;
* file uploads should be more restricted than reading a list of records;
* administrative operations should have tighter controls than standard user actions.
Exact numeric limits must be based on observed usage patterns, testing, and operational requirements. Do not hard-code arbitrary values into the source-of-truth documentation and present them as permanent business rules.

System Behavior When Limits Are Exceeded
When a request exceeds the allowed limit:
* the request must be rejected by the backend;
* the response must clearly indicate that the limit has been exceeded;
* the event should be logged when appropriate for security monitoring;
* repeated abuse may trigger additional protective actions according to operational policies.
The system must fail safely and must not expose sensitive implementation details in error messages.

Logging and Monitoring
Rate-limiting events should be considered for security monitoring, especially:
* repeated login failures;
* repeated password reset requests;
* excessive attendance requests;
* repeated QR validation failures;
* excessive file uploads;
* administrative action abuse attempts.
Logs should include:
* timestamp;
* event type;
* affected operation;
* user identifier when available;
* IP address or request origin where available;
* result (allowed, limited, or blocked).

Cross-Platform Requirement
Rate limiting rules apply equally to:
* mobile application requests;
* web application requests;
* administrative interfaces;
* API integrations if introduced in future approved versions.
Rate limiting is a backend responsibility and must not depend on the client platform.

# Row Level Security (RLS)

## Purpose

The system shall use PostgreSQL Row Level Security (RLS) to ensure that authenticated users can only access data they are explicitly authorized to view or modify.

RLS acts as a database-level security layer and remains effective even if an API endpoint is incorrectly implemented.

The backend and database must never rely solely on frontend restrictions.

---

## General Principles

Row Level Security shall be enabled on all tables containing user-specific or sensitive information.

Access must be granted using explicit policies rather than unrestricted queries.

Every query executed by an authenticated user must be evaluated against the applicable RLS policy before data is returned.

If no policy permits access, the database shall deny the request.

---

## Student Access

Students may access only their own records.

Examples include:

- profile information
- attendance records
- internship progress
- submitted reports
- received notifications
- evaluation results, if authorized

Students shall not access records belonging to other students.

---

## OJT Coordinator Access

OJT Coordinators may access records required to perform academic and administrative responsibilities.

Examples include:

- registered students
- attendance records
- internship progress
- reports
- company assignments
- supervisor assignments

Coordinator permissions shall follow the approved Roles and Permissions document.

---

## Company Supervisor Access

Company Supervisors shall access only students officially assigned to them.

They may view only information necessary to:

- verify attendance
- review attendance evidence
- complete evaluations

Supervisors shall not access unrelated student records.

---

## Program Head Access

Program Heads may access monitoring information authorized by institutional policy.

Access shall remain read-only unless additional permissions are officially approved.

---

## Admin Access

The Admin role manages technical system administration.

Administrative database access shall follow the principle of least privilege.

Admin privileges shall not automatically include academic authority.

---

## Principle of Least Privilege

Every role shall receive only the minimum database permissions necessary to perform assigned responsibilities.

Additional access shall not be granted unless explicitly approved.

---

## Direct Database Protection

Security shall not depend solely on API validation.

Even if an API endpoint contains a defect, RLS policies shall continue protecting unauthorized records.

Database-level authorization is mandatory.


# Insecure Direct Object Reference (IDOR) Protection

## Purpose

The system shall prevent Insecure Direct Object Reference (IDOR) vulnerabilities.

A user must never gain access to another user's resources simply by modifying an identifier such as:

- user_id
- student_id
- report_id
- attendance_id
- evaluation_id
- notification_id
- company_id

Authorization shall always be verified before data is returned.

---

## Authorization Before Resource Access

Every request for protected resources shall verify:

1. Authentication
2. User role
3. Ownership or assigned permission
4. Requested operation

Only after successful verification may the requested resource be accessed.

---

## Ownership Verification

Examples include:

Students may only access:

- their own attendance
- their own reports
- their own internship progress
- their own notifications

Company Supervisors may only access:

- students assigned to them
- attendance records requiring their verification
- evaluations they are authorized to complete

OJT Coordinators shall access records according to approved responsibilities.

Program Heads shall access only authorized monitoring information.

---

## Resource Identifier Validation

The application shall never assume that possession of an identifier grants access.

Every identifier received from the client shall be validated against the authenticated user's permissions.

Changing a URL parameter or request body must never allow unauthorized access.

---

## Secure API Design

Every protected endpoint shall enforce authorization regardless of:

- hidden UI elements
- disabled buttons
- frontend navigation restrictions

The backend remains the final authority.

---

## Error Responses

Unauthorized access attempts shall return generic authorization errors.

The system shall not reveal:

- whether a resource exists
- resource ownership
- internal identifiers
- database structure

This prevents information disclosure.

---

## Logging

Unauthorized access attempts should be recorded in audit logs.

Logs should include:

- authenticated user
- requested resource
- timestamp
- endpoint
- action attempted

Sensitive information shall not be exposed in logs.
